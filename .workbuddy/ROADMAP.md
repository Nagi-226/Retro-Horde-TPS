## 📋 项目契约 (Project Contract — M1)

```
═══════════════════════════════════════════════════════════════
项目名称: Retro Horde
项目类型: 第三人称复古弹幕生存射击 (单人开发 + AI辅助)
引擎版本: Godot 4.6.2 (GDScript 2.0)
基线代码: godotengine/tps-demo (15 .gd / 17 .tscn)

核心范围 (Scope):
  v0.0.2: 波次系统 + 弹幕模式 + HP/得分/HUD
  v0.1.0: 完整可玩版本（不超过5种敌人/3种武器/3张地图）

架构约束 (Architecture Constraints):
  - GDScript 100%静态类型
  - Composition over Inheritance (节点组合，拒绝深层继承)
  - EventBus Autoload 跨场景通信
  - 所有新功能在现有场景结构上渐进扩展
  - 保持 ENET 多人兼容（不破坏现有RPC/同步机制）

明确排除 (Exclusions):
  ❌ 不做程序化地图生成（v0.1.0前）→ 手工设计3张关卡
  ❌ 不做行为树AI系统 → 状态机足够覆盖5种敌人
  ❌ 不做多语言本地化 → 英文UI
  ❌ 不做手机端适配 → 仅Windows桌面
  ❌ 不做存档系统（v0.1.0前）→ 最高分用ConfigFile
  ❌ 不做在线排行榜 → 本地排行榜
  ❌ 不做技能树/天赋系统 → 纯武器+走位
  ❌ 不做剧情/对话系统 → 纯街机体验

风险登记 (Risk Register):
  R1: 弹幕密度过高导致性能下降 → 上限200投射物，对象池管理
  R2: 多人同步下弹幕状态暴增 → 仅Host权威生成弹幕
  R3: 敌人AI多样化导致代码重复 → 抽象EnemyBase + 状态机复用

契约建立于: 2026-05-20
═══════════════════════════════════════════════════════════════
```

## 🎯 v0.0.2 — 弹幕生存核心机制

> **目标**: 5分钟内从"TPS Demo"变为"弹幕生存游戏"的可玩原型
> **工期**: 建议 1-2 周
> **DoD**: 运行 `run_game.bat` → 一波敌人出现 → 发射弹幕 → 玩家有HP → 击杀得分 → HUD显示全部信息

### v0.0.2 DoD (验收标准)

```
[v0.0.2 Done] 所有条件满足:
□ 启动游戏 → 第1波3个敌人自动生成
□ 波次递增 → 每波敌人数量+2，弹幕密度增加
□ 敌人发射扇形弹幕 (至少3方向) 替代单一激光
□ 玩家中弹 → HP条减少 (HUD左上)
□ HP归零 → 玩家死亡动画 + "Game Over" + 得分
□ 击杀敌人 → 得分增加 + HUD右上更新
□ HUD显示: 波次号 | 得分 | HP条 | 剩余敌人
□ 多人模式 (host/client) 波次同步正常
□ 弹幕上限200个投射物 → 对象池回收 → 无卡顿
```

### 风险缓解

| 风险 | 缓解措施 |
|------|---------|
| 弹幕过多导致掉帧 | 对象池 (预分配200个Bullet节点)，超出则最老子弹回收 |
| 多人同步弹幕状态爆炸 | 仅 Host 端 spawn 弹幕，Client 端纯显示 (MultiplayerSpawner) |
| HP/得分 跨场景丢失 | EventBus Autoload 保证信号跨场景可达 |

## 🎯 v0.1.0 — 完整可玩版本（收敛版）

### 收敛后的范围（vs 原计划）

| 原计划 | 收敛后 | 理由 |

| 完整游戏循环 (菜单→选关→战斗→结算→排行榜) | 菜单→战斗→结算 (无选关，顺序通关) | 3关顺序解锁比选关UI省2周 |

| 平衡性调整 | 基于 playtest-report 一轮数值调整 | 平衡是迭代过程，不是一次性工作 |
| 打包发布 | Windows .exe 导出 (.pck打包) | Godot一键导出，无需安装包 |
